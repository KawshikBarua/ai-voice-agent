01  System overview

A multi-tenant SaaS that answers inbound phone calls with an AI voice agent and gives each tenant a dashboard for appointments, customers, catalogue, knowledge and analytics. The platform is industry-independent: behaviour adapts by configuration, not by code changes.

Runtime topology

  Caller ──telephony──▶  Retell AI (STT · LLM · TTS)
                            │  ├── live-call tool calls ──▶ POST /api/v1/ai/tools/{orgId}/*
                            │  └── lifecycle webhooks   ──▶ POST /api/v1/webhooks/retell
                            ▼
                     ASP.NET Core 8 Web API  ◀── REST/JWT ── React SPA (Vite)
                            │
                            ▼
                     SQL Server  ·  AiDB

Design principles

  • The database is the source of truth. The AI never answers from memory for prices, availability or bookings — it calls back into this API, which reads AiDB.
  • Tenant isolation is structural. Every tenant-owned table carries OrganizationId; every query filters on the value resolved from the JWT.
  • Core AI instructions are platform-owned. Tenants supply data only; the safety rules cannot be edited by them.
  • Nothing is hard deleted. Tenant data uses IsDeleted soft delete; audit rows are append-only.

Two directions of traffic

Understanding the integration means separating them. Outbound: we push configuration to the voice provider (agent, prompt, tools, knowledge base). Inbound: the provider calls us during and after calls (tool functions, webhooks). They authenticate differently — see sections 11–13.

04  Multi-tenancy model

One row in Organizations is one tenant. Isolation is enforced at three layers.

1 — Claim

TokenService writes an orgId claim into every access token. TenantProvider reads it per request and throws UnauthorizedAccessException if absent.

public int OrganizationId =>
    int.TryParse(Principal?.FindFirstValue("orgId"), out var id)
        ? id : throw new UnauthorizedAccessException("Missing organization claim.");

2 — Query

Every repository method takes orgId and includes it in the WHERE clause. There is no code path that reads a tenant table without it.

3 — Schema

Every tenant-owned table has a non-nullable OrganizationId foreign key.

Rule for new code

A repository method that touches a tenant table and does not accept orgId is a bug. Controllers must pass _tenant.OrganizationId — never a value from the request body, which a client could forge.

Inbound provider traffic

Tool calls and webhooks arrive without a JWT, so the tenant is resolved differently:

  • Tool calls — orgId is a path segment in the URL registered with the provider, protected by a per-tenant token (section 12).
  • Webhooks — resolved by looking up the payload's agent_id against AgentConfig.RetellAgentId (section 13).

06  Authentication & authorization

Token flow

  1. POST /auth/login verifies the BCrypt hash and issues a short-lived access token (15 min) plus a refresh token (7 days, persisted).
  2. The SPA stores both in Zustand (persisted to localStorage) and attaches the access token as a Bearer header via an axios interceptor.
  3. On 401, the interceptor calls POST /auth/refresh once, rotates both tokens, and replays the original request. Concurrent 401s share one refresh promise.
  4. Refresh rotates: the presented token is revoked and a new one issued, so a stolen refresh token is single-use.

Access token claims

sub   = user id          orgId = tenant id      (custom claim)
email = user email       role  = RBAC role      jti = token id

Roles

RoleScope

OrgAdminFull control of one tenant, including organisation settings
ManagerCatalogue, knowledge base, agent settings, operations
ReceptionistAppointments and customers

Two composite constants avoid drift across controllers:

Roles.Staff      = SuperAdmin, OrgAdmin, Manager, Receptionist   // operations
Roles.Management = SuperAdmin, OrgAdmin, Manager                 // configuration

Lesson learned

Roles were originally listed inline per endpoint and SuperAdmin was omitted, making the platform operator less privileged than a tenant admin — buttons silently returned 403. Always use the constants for new endpoints.

09  Prompt architecture

PromptBuilderService splits tenant content by how the model needs it. This is a cost decision as much as a quality one: prompt tokens are billed on every conversational turn, knowledge-base content is retrieved only when relevant.

Emergency rules stay in the prompt deliberately

Retrieval is probabilistic — a document may not be fetched. Safety instructions ("tell the caller to shut off the water main", "advise them to leave the property") must be present on every turn, so they are never moved to the knowledge base.

Interface

Task<string> BuildSystemPromptAsync(int orgId);
Task<List<KnowledgeDocument>> BuildKnowledgeDocumentsAsync(int orgId);

public record KnowledgeDocument(string Title, string Text);

Composition order

Role line ("You are a plumbing company receptionist for X, a Y business")
  + Core rules      // platform-owned constant, never tenant-editable
  + Industry rules  // from IndustryTemplates
  + Conversation flow
  + Business details (+ field-service note when applicable)
  + Business hours (raw JSON)
  + Emergency rules (KnowledgeBase category = EmergencyRule)
  + Tool usage guide

The core rules constant encodes the non-negotiables: introduce as AI, never invent prices or availability, always use tools for live data, transfer when uncertain, confirm before mutating, one question at a time.

Observed sizes on the demo tenant: system prompt ≈ 2,960 characters; knowledge documents ≈ 1,340 characters across five documents. The gap widens sharply for tenants with large catalogues — which is the point.

10  Industry templates

IndustryTemplates.Resolve(industry) maps the free-text Organizations.Industry to an IndustryProfile, falling back to a generic premises-based receptionist. Matching is substring-based with a synonym pass ("plumber" → plumbing, "attorney" → legal, "clinic" → medical).

public record IndustryProfile(
    string   Role,            // "a plumbing company receptionist"
    bool     IsFieldService,  // technician travels to the caller
    string   CustomerNoun,    // customer | patient | client
    string[] ConversationFlow,
    string[] ExtraRules);

The critical axis: field service vs premises

AspectPremises-basedField service
ExamplesClinics, salons, workshops, law firmsPlumbing, electrical, HVAC, locksmith, cleaning
Flow length8 steps10 steps
Service addressNot collectedMandatory — enforced in the tool schema and server-side
Urgency triageNot promptedListens for leak / no power / no heat / lockout
Pricing languageQuoted rangeRange, plus "final price depends on what the technician finds"

Eleven profiles ship today: medical, dental, plumbing, electrical, HVAC, locksmith, cleaning, automotive, salon, legal, consulting.

Adding an industry

Add an entry to the Profiles dictionary with its role string, field-service flag, customer noun and safety rules. No other code changes — the prompt, tool schema and required-field list all derive from the profile.

11  Voice provider integration (outbound)

RetellService.SyncAgentAsync(orgId) pushes a tenant's configuration to Retell AI. It is guarded by a per-organization SemaphoreSlim so the manual button and the background worker can never create duplicate resources.

Provider endpoints called

EndpointUsed for
POST/create-retell-llmFirst sync: prompt + tools + knowledge base ids
PATCH/update-retell-llm/{llm_id}Subsequent syncs
POST/create-agentFirst sync: voice, language, response engine, webhook
PATCH/update-agent/{agent_id}Subsequent syncs
POST/create-knowledge-baseMultipart upload of reference documents
DEL/delete-knowledge-base/{kb_id}Remove the superseded knowledge base
POST/v2/list-callsCall reconciliation (section 13)

Authenticated with Authorization: Bearer {Retell:ApiKey}. Provider API calls are not separately billed; usage is billed per call minute.

Sync sequence

  1. Guards — API key configured; PublicBaseUrl must not be localhost (the provider rejects unreachable tool/webhook URLs).
  2. Knowledge base — build documents, upload as a new KB, capture its id.
  3. LLM — POST or PATCH with general_prompt, begin_message, general_tools, knowledge_base_ids.
  4. Persist immediately — write ids to AgentConfig before doing anything else, so a later failure cannot orphan a created resource.
  5. Delete the previous KB — only now, once the LLM no longer references it.
  6. Agent — POST or PATCH with voice, language, response_engine = { type: "retell-llm", llm_id } and webhook_url.
  7. Persist agent id and LastSyncedAt.

Ordering is a correctness requirement, not style

Create-then-swap-then-delete guarantees the agent always references a live knowledge base. Deleting first would leave a window where the agent points at nothing. Persisting ids immediately after creation prevents orphaned billable resources if the process dies mid-sync.

Provider-specific gotchas

  • E.164 only — transfer numbers must be +15550100199, no spaces. PhoneUtil.Normalize is applied before sending. Fictional numbers (555 area code) are rejected outright.
  • transfer_call requires transfer_option — omitting it fails schema validation.
  • Only Retell platform voices are offered — retell-Grace, retell-Ashley, retell-Chloe, retell-Nico (Shared/RetellVoices.cs). enable_expressive_mode is on for every tenant and Retell honours it for platform voices only, so MapVoice settles anything else onto this set, matching older provider-prefixed ids by name.
  • Knowledge bases are immutable once indexed — content changes mean creating a new one and swapping.

12  Live-call tool endpoints (inbound)

During a call the model invokes HTTP functions registered on the LLM. These are what make the AI factual — every slot and booking round-trips to AiDB.

ToolRequired argumentsBehaviour
identify_customerphonePhone → email → name lookup; returns visit count
check_availabilitydateSlots honouring business hours, capacity and past-time exclusion
book_appointmentname, phone, service, start_time (+ service_address for field service)Creates customer if new, atomic capacity-checked insert, timeline event
cancel_appointmentphone, nameName verification; disambiguates by date/service
reschedule_appointmentphone, name, new_timeConflict-checked move
check_appointmentphoneNext booking with status and payment status

Plus provider built-ins end_call and transfer_call.

There is deliberately no pricing tool. The service and product catalogues are uploaded to the knowledge base on every sync, so the model already has them in context: a round-trip per price question bought nothing but a silence in the middle of the answer. Prices are therefore as at the last sync — stable enough for prices, and the catalogue document says out loud that stock counts are an indication rather than a promise.

Authentication — the important part

Tool calls are NOT signed by the provider

Only webhooks carry X-Retell-Signature. Custom function calls are plain POSTs. An early implementation validated a signature on tool calls and returned 401 to every one of them — calls failed mid-conversation with "a technical error".

Because we generate the tool URLs during sync, the secret travels in the URL:

token = HMACSHA256(apiKey, $"tools:{orgId}")  → hex, first 32 chars

https://host/api/v1/ai/tools/1/book_appointment?k=36e98a8ba82d...

It is unguessable without the API key, scoped per tenant, and needs no storage. RetellSignature.AcceptToolCall accepts a valid token or a valid signature, and rejections log which credential was missing.

Response contract

Return JSON whose result string is written as an instruction to the model, not as UI copy — the model reads it and acts on it:

{ "result": "That time was just taken. Use check_availability to offer alternatives." }
{ "result": "A service address is required before booking. Ask for the full street
             address, city, and any access details such as apartment or gate code." }

This is a server-side guardrail: even if the model calls a tool prematurely, the response steers it back on track.

13  Webhooks & call reconciliation

Webhook — POST /api/v1/webhooks/retell

Anonymous, verified by X-Retell-Signature (HMAC-SHA256 of the raw body keyed with the API key). The raw stream is read before deserialisation because the signature covers the exact bytes.

{ "event": "call_ended",
  "call": { "call_id", "agent_id", "from_number", "transcript",
            "recording_url", "start_timestamp", "end_timestamp",
            "disconnection_reason", "call_analysis": { "call_summary" } } }
  • call_ended → store the call log, match the customer by phone, write an AiCall timeline event.
  • call_analyzed → attach the summary; falls back to storing the call if the earlier event was missed.
  • Tenant resolved via agent_id → AgentConfig. Unknown agents are acknowledged with 200 so the provider stops retrying.
  • Duplicate deliveries are suppressed by checking RetellCallId first.

disconnection_reason maps to status: dial_no_answer / dial_busy / dial_failed → Missed; call_transfer → Transferred; otherwise Completed.

Reconciliation — why webhooks alone are not enough

Webhooks are fire-and-forget. If the API or tunnel is down when a call ends, that history is lost permanently. BackfillCallsAsync pulls the last 100 calls for the tenant's agent from POST /v2/list-calls and inserts any whose RetellCallId is not already stored.

It runs automatically on API startup for every connected tenant, and on demand via POST /calls/sync. Idempotent, so it is safe to run repeatedly.

Web test calls have no caller ID; from_number is stored as web-call and cannot be auto-linked to a customer.

14  Background workers

RetellSyncWorker is a BackgroundService consuming an unbounded Channel<int> of organization ids.

public interface IRetellSyncQueue {
    void Enqueue(int orgId);
    ChannelReader<int> Reader { get; }
}

Producers

Controllers call _retellSync.Enqueue(orgId) after any mutation that changes what the AI should know: services, products, knowledge base entries, organization settings, agent settings.

Consumer behaviour

  • Skips tenants with no RetellAgentId — the worker never creates provider resources implicitly; that is an explicit operator action.
  • On startup, enqueues every connected tenant (so a changed public URL propagates) and runs call backfill for each.
  • Exceptions are logged and swallowed per item; one bad tenant cannot stop the loop.

Scaling note

The queue is in-process and non-durable — enqueued work is lost on restart, mitigated by the startup re-sync. For horizontal scaling this should move to a distributed queue so the work is executed exactly once across instances.

16  Correctness & edge cases

Non-obvious behaviours that exist because the naive implementation was wrong.

Concurrent booking

Check-then-insert races when two calls are live simultaneously. Booking is a single statement inside a transaction using range locks. With no roster on file, capacity is one number for the whole business:

INSERT INTO Appointments (...) OUTPUT INSERTED.Id
SELECT @... WHERE
  (SELECT COUNT(*) FROM Appointments WITH (UPDLOCK, HOLDLOCK)
   WHERE OrganizationId=@o AND IsDeleted=0
     AND Status NOT IN ('Cancelled','Missed')
     AND StartAt < @EndAt AND EndAt > @StartAt)
  < (SELECT ISNULL(MaxConcurrentAppointments,1) FROM Organizations WHERE Id=@o)

Returns null when the slot is full — callers translate that to 409 or a spoken "that time was just taken".

Parallel bookings across a team

Once an organization has employees, how many appointments may overlap stops being a property of the business and becomes a property of the slot: it is however many people are on duty then and not already with someone. Two employees means two callers can both be given 12:00, one each; nobody on duty means neither can, whatever the business hours say.

StaffRoster settles who is on duty — active, their own weekly hours cover the slot end to end (intersected with the business hours), and no EmployeeTimeOff over that date. Who is free is settled in SQL, under the same locks as the write, because that is the only place it can be settled against a second call happening at the same moment:

SELECT @FreeOnDuty = COUNT(*) FROM Employees e
WHERE e.Id IN @OnDutyIds
  AND NOT EXISTS (overlapping appointment for e.Id, UPDLOCK/HOLDLOCK);

IF @FreeOnDuty > @Unassigned          -- bookings over the slot with nobody named
SELECT TOP 1 @Chosen = e.Id FROM Employees e
WHERE e.Id IN @CandidateIds AND NOT EXISTS (overlapping appointment)
ORDER BY CHARINDEX(',' + CAST(e.Id AS NVARCHAR(12)) + ',', @CandidateOrder), e.Id;

INSERT INTO Appointments (..., EmployeeId, ...)
SELECT ..., @Chosen, ... WHERE @Chosen IS NOT NULL;

@Unassigned is what keeps a tenant honest when they build a roster after they already had bookings: an appointment with nobody named still occupies one person, so two employees never read as three parallel slots. @CandidateOrder carries the caller's preference — anyone at all for the AI, one named person for a dashboard booking, the current holder first for a reschedule, so moving a booking does not needlessly move the person. check_availability applies the same rule when listing a day, which is why a time can still come back free straight after being booked for someone else.

Time zones

Appointments are stored in UTC; callers and the AI speak tenant-local time. TenantTime converts at the boundary using Organizations.Timezone. Dashboard "today" is computed from tenant-local midnight, not GETUTCDATE().

Phone numbers

PhoneUtil.Normalize reduces to + plus digits. Applied on every write and lookup, with a trailing-nine-digit fallback so a missing country code still matches. Verified: +1 (555) 010-0888, 555-010-0888 and 5550100888 resolve to one customer.

Business hours

BusinessHours.For(json, dayOfWeek) parses {"mon-fri":"09:00-17:00","sat":"10:00-14:00","sun":"closed"}, supporting single days, ranges and wrapped ranges. A configured JSON that omits a day means closed; absent configuration falls back to 09:00–17:00 daily.

Design tokens

Defined once in index.css under Tailwind v4's @theme: page #b7d5d4, panel #f2f2ee, card white, ink #1c1c1c, accent #f4ec7a, plus lavender/mint/cream chips and sky/leaf chart colours. Cards use a 24px radius, buttons are full pills.

Cache invalidation

Mutations invalidate the query keys they affect — for example confirming an appointment invalidates ['appointments'], ['dashboard'] and ['sidebar-counts'], so badges and figures update without a reload.

Surface failures

Mutations must render their errors. Silent catch blocks previously made 403 responses look like dead buttons — the appointment actions now show the server message and a per-button busy state.

Recommended next steps

  1. Encryption at rest for customer PII — the largest compliance gap.
  2. Durable job queue to replace the in-process channel before scaling out.
  3. Per-tenant usage metering — sum CallLogs.DurationSeconds by organization; this is the basis of both billing and cost control.
  4. Knowledge-base thresholding — provider knowledge bases carry a monthly fee each; keep small catalogues inline in the prompt and only create a KB above a size threshold.
  5. Field-service depth — travel-time buffers, call-out fees, technician skill matching.
  6. Email notifications — confirmations and reminders are the highest-value missing customer-facing feature.

Scale considerations

The SRS targets 10,000+ organizations. At that scale: the sync queue must be distributed; per-tenant provider knowledge bases become a material recurring cost; dashboard aggregates should be cached rather than computed per request; and CallLogs.Transcript growth warrants partitioning or archival.
